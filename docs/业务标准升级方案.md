当前版本已整理到改造点 14，统一按以下结构编写：

- 改造目标
- 逻辑改造
- 页面改造
- 影响范围及兼容性说明

## 改造点 1：关键数据算法下拉改为本地 JSON 配置

### 1. 改造目标

将当前页面中写死的关键数据算法 1/2/3/4，改为通过本地 UTF-8 JSON 文件统一维护，并在服务启动时读取到内存后使用。

### 2. 逻辑改造

#### 2.1 配置文件

配置文件路径：server/config/business-algorithms.json

建议配置结构：

| 配置项 | 示例值 | 说明 |
| --- | --- | --- |
| value | 1 | 算法编码，对应 gjsjsf / ywsf |
| label | 最大可提取额 | 算法名称 |
| sort | 1 | 排序号 |
| enabled | true | 是否启用 |

建议初始配置保留现有 4 个算法：

| 编码 | 名称 |
| --- | --- |
| 1 | 最大可提取额 |
| 2 | 最高可贷金额 |
| 3 | 最高可贷年限 |
| 4 | 借款人最大可对冲支取金额 |

#### 2.2 后端处理

- 服务启动时统一读取 JSON 文件并缓存到内存。
- 下拉数据、名称映射和算法合法性校验统一使用该内存配置。
- 配置变更采用“修改文件后重启服务生效”的方式。

#### 2.3 存储与校验

- gjj_ywbzk.gjsjsf 和 gjj_ywbz.ywsf 继续保存算法编码。
- 不新增数据库表，不调整现有字段结构。
- 标准库和业务规则相关保存接口增加算法编码合法性校验。

### 3. 页面改造

| 页面 | 调整内容 |
| --- | --- |
| 标准库页面（server/templates/pages/business_standard.j2） | 查询区算法下拉改为动态取值；新增、编辑弹窗中的算法下拉改为动态取值；列表中的算法名称展示改为动态映射。 |
| 业务规则页面（server/templates/pages/business_rule.j2） | 查询区算法下拉改为动态取值；清册选择弹窗中的算法相关筛选改为动态取值；列表中的算法名称展示改为动态映射。 |

### 4. 影响范围及兼容性说明

| 类别 | 内容 |
| --- | --- |
| 配置文件 | server/config/business-algorithms.json |
| 页面模板 | server/templates/pages/business_standard.j2；server/templates/pages/business_rule.j2 |
| 后端逻辑 | 算法配置读取、缓存、名称映射、接口校验 |
| 兼容性说明 | 不改数据库表结构；不改现有算法编码字段；不影响现有 1/2/3/4 数据；后续新增算法时只需增加 JSON 配置并同步补充对应逻辑。 |

### 5. 已上线数据库投产 SQL

本改造点仅涉及本地 JSON 配置和服务启动时的内存缓存，不涉及数据库新增表或新增字段。

- Oracle：无需执行数据库 DDL。
- 达梦：无需执行数据库 DDL。
- 人大金仓：无需执行数据库 DDL。

## 改造点 2：业务内容分类改为自有维护并通过自有接口取值

### 1. 改造目标

将当前依赖平台接口返回的业务内容分类，改为由系统自有表维护并通过自有接口提供，同时支持在标准库页面中新增、修改、删除业务内容分类。

业务内容分类与关键数据算法存在关联关系，因此分类基础数据需按关键数据算法维度维护。

### 2. 逻辑改造

#### 2.1 业务内容分类基础表

新增表：gjj_ywnrfl

建议字段：

| 字段名 | 说明 |
| --- | --- |
| id | 主键 |
| gjsjsf | 所属关键算法编码 |
| flbm | 业务内容分类编码 |
| flmc | 业务内容分类名称 |
| pxh | 排序号 |
| sfqy | 是否启用 |
| cjsj | 创建时间 |
| gxsj | 更新时间 |

#### 2.2 下拉接口

- 原 tools/business-content-classes 接口由调用平台接口改为查询 gjj_ywnrfl 表。
- 查询时按当前 gjsjsf 过滤，仅返回启用数据，按 pxh、id 排序。
- 返回结构保持不变：value 对应 flbm，label 对应 flmc。

#### 2.3 存储方式

- gjj_ywbzk.ywnrfl 和 gjj_ywbz.ywnrfl 继续保存分类编码。
- 本次仅调整分类数据来源，不调整现有字段结构。

#### 2.4 分类维护能力

需新增 gjj_ywnrfl 的基础 CRUD 接口，支持新增、修改、删除。

维护约束：

| 约束项 | 说明 |
| --- | --- |
| 关键算法必填 | 新增和修改时必须选择所属关键算法 gjsjsf |
| 编码唯一性 | flbm 建议在同一关键算法下唯一 |
| 删除校验 | 删除前需校验是否已被标准库或业务规则引用 |

#### 2.5 基础数据初始化

上线前需初始化现有业务内容分类数据，可通过初始化 SQL、后台脚本或数据库手工维护完成。

### 3. 页面改造

| 页面 | 调整内容 |
| --- | --- |
| 标准库页面（server/templates/pages/business_standard.j2） | 业务内容分类下拉改为调用自有接口；下拉按当前关键算法联动过滤；新增工具栏按钮“业务内容分类维护”；维护弹窗支持新增、修改、删除；新增、修改表单中增加“关键数据算法”下拉。 |
| 业务规则页面（server/templates/pages/business_rule.j2） | 查询区业务内容分类下拉改为调用自有接口；下拉按当前关键算法联动过滤；清册选择弹窗中的业务内容分类筛选改为调用自有接口；列表中的业务内容分类名称改为基于自有数据源展示。 |

页面边界：本次不新增独立的业务内容分类管理页面，统一通过标准库页面按钮弹窗维护。

### 4. 影响范围及兼容性说明

| 类别 | 内容 |
| --- | --- |
| 数据库结构 | 新增 gjj_ywnrfl 表及 gjsjsf 字段 |
| 页面模板 | server/templates/pages/business_standard.j2；server/templates/pages/business_rule.j2 |
| 后端逻辑 | server/routes/http/tools.js 及业务内容分类 CRUD、查询、联动过滤逻辑 |
| 兼容性说明 | 不调整 gjj_ywbzk.ywnrfl、gjj_ywbz.ywnrfl 字段结构；不改变现有分类编码存储方式；历史数据可继续使用；上线前需完成 gjj_ywnrfl 基础数据初始化。 |

### 5. 已上线数据库投产 SQL

本改造点的投产 SQL 已拆分到独立脚本，请按数据库类型执行对应文件中的“改造点 2”段落：

## 改造点 3：标准库新增自定义编码字段

### 1. 改造目标

在标准库中新增稳定、可维护的业务标准编码字段，为后续程序和存储过程按编码识别业务办理标准提供统一基础。

### 2. 逻辑改造

#### 2.1 新增字段

在 gjj_ywbzk 表中新增字段：zdybm

字段要求：

| 要求项 | 说明 |
| --- | --- |
| 可维护 | 支持手工录入和修改 |
| 唯一性 | 同一标准库内保持唯一 |
| 取值规范 | 建议使用英文、数字、下划线等稳定字符 |

#### 2.2 标准库读写逻辑

标准库相关接口和导入导出逻辑需同步支持 zdybm：

- 列表查询
- 详情查询
- 新增保存
- 编辑保存
- 导入导出

#### 2.3 后续使用方式

后续程序或存储过程识别业务标准时，应优先基于 zdybm 判断，不再优先依赖 ywblbz、id 或页面展示名称。

#### 2.4 历史数据处理

字段新增后，需为已有标准库数据逐步补齐编码；若后续逻辑依赖 zdybm，则对应标准必须先完成补码。

| 业务规则页面 | 本次原则上不新增维护入口；如有需要，可在后续版本增加只读展示。 |

页面边界：本次只解决标准库自定义编码可维护的问题，不扩展为独立编码管理体系。

### 4. 影响范围及兼容性说明

## 改造点 6：关键数据算法按不同子存储过程执行

### 1. 改造目标

将当前集中在同一个主存储过程中的关键算法执行逻辑，调整为“统一入口分发 + 不同关键算法调用不同子存储过程”的方式，降低耦合并提升扩展性。

### 2. 逻辑改造

#### 2.1 保留统一入口

统一入口过程继续作为外部调用入口，负责接收入参、按关键算法编码分发到对应子存储过程，并汇总最终结果。

#### 2.2 拆分子存储过程

建议按算法拆分为独立子存储过程：

- 最大可提取额
- 最高可贷金额
- 最高可贷年限
- 借款人最大可对冲支取金额

后续新增算法时，继续按相同模式增加子存储过程。

#### 2.3 通用能力下沉

以下能力建议继续保留为公共函数或公共逻辑：

- 方言 SQL 解析
- 标准值解析
- 页面参数读取
- 动态 SQL 预处理
- 执行日志写入

#### 2.4 调用关系

- 外部程序继续调用统一入口。
- 统一入口按算法编码分发。
- 子存储过程只处理本算法相关逻辑。

## 改造点 9：调试功能支持业务参数自动生成及成功案例保存反显

### 1. 改造目标

在关键数据计算模型的调试功能中，调试 JSON 入参不再完全依赖人工手写，而是根据当前关键数据算法、业务内容分类及业务参数定义自动生成基础入参模板。配置人员只需按调试需要修改参数值即可发起验证。同时支持将调试成功的请求参数保存为案例，供其他人员直接选择、反显并复用。

### 2. 逻辑改造

#### 2.1 调试入参自动生成

- 打开调试弹窗时，系统根据当前算法、业务内容分类和调试参数定义自动生成 JSON 模板。
- 模板中默认带出必要业务参数，例如关键算法编码、业务内容分类、机构编号及该算法对应的常用业务字段。
- 对于可推导的字段优先自动填充默认值或示例值，减少人工拼装成本。

#### 2.2 成功案例保存

- 当一次调试执行成功后，支持将本次请求参数保存为“调试成功案例”。
- 保存内容建议至少包括：算法编码、业务内容分类、案例名称、请求参数 JSON、调试结果摘要、创建人、创建时间。
- 同一算法下可保存多条案例，便于覆盖不同业务场景。

#### 2.3 案例反显与复用

- 调试弹窗中增加“选择案例”或“历史成功案例”入口。
- 选中某个成功案例后，自动将其请求参数反显到 JSON 编辑器中，配置人员可直接再次调试，或在此基础上修改少量字段后验证。
- 反显时保留案例原始结构，避免字段缺失或顺序混乱影响理解。

#### 2.4 前端改造点

- `server/templates/pages/business_rule.j2` 中调试弹窗需增加“自动生成入参”“保存案例”“选择案例/反显案例”相关交互。
- JSON 编辑器初始化时优先加载自动生成模板；选择案例后覆盖当前编辑区内容。
- 调试成功后按钮区支持一键保存当前请求参数为案例。
- 案例列表建议展示案例名称、算法、业务内容分类、创建人、创建时间，并支持点击后反显。

#### 2.5 后端改造点

- 新增调试入参模板生成接口，按算法和业务内容分类返回推荐 JSON 结构。
- 新增调试案例保存、查询、详情接口，支持按算法、业务内容分类过滤。
- 保存案例时建议校验 JSON 合法性，并限制仅保存调试成功的数据，避免无效样例沉淀。
- 详情接口返回时需保持 JSON 原始结构，确保前端反显一致。

#### 2.6 数据影响说明

- 建议新增调试案例表，按算法、业务内容分类和案例维度存储请求参数样例。
- 如暂不建表，也可先采用 JSON 文件或其他配置存储，但长期建议落库以支持检索、权限和审计。
- 历史未保存案例的数据不受影响，原有手工调试方式仍可保留作为兜底。

## 改造点 11：标准库属性组支持自定义属性录入

### 1. 改造目标

在标准库页面的“业务办理标准属性组”中，除现有“对象属性”选择方式外，新增“自定义属性”录入方式。

当选择“自定义属性”时，允许直接录入“属性名称”和“属性编码”，并继续复用现有 `gjj_ywbzksx` 表保存配置；同时业务规则页面在配置参数时，应支持对这类自定义属性手工录入值。

### 2. 逻辑改造

#### 2.1 页面模式切换

标准库新增、修改页面中的“业务办理标准属性组”区域调整为 3 列展示，并新增“是否对象属性”开关，默认值为“是”。

- 选择“是”时，保持现有逻辑不变，继续选择所属对象、业务标准属性、属性来源及来源 SQL。
- 选择“否”时，隐藏“所属对象”“业务标准属性”“属性来源”“来源 SQL”等现有对象属性相关项，仅保留“属性名称”“属性编码”两个输入项。

#### 2.2 配置存储方式

本次改造继续使用现有表：`gjj_ywbzksx`，不新增表，不新增“是否对象属性”数据库字段。

当“是否对象属性=是”时，按当前方式保存，不调整现有字段含义。

当“是否对象属性=否”时，建议按下表保存：

| gjj_ywbzksx 字段 | 保存值 | 说明 |
| --- | --- | --- |
| ywblbzdx | 空 | 不关联对象属性 |
| fwdxbq | 空 | 不关联对象标签 |
| sxbm | 属性名称 | 作为页面展示名称 |
| ywblbzsx | 属性编码 | 作为参数编码和取值键 |
| sxly | page | 继续按页面取值处理 |
| ywblbzyg | 空 | 不再配置来源 SQL |

说明：

- 本次不建议新增 `sxly=zdy` 之类的新取值。
- `sxly` 仍保持现有语义，仅使用 `page/sql` 两种模式。
- 自定义属性固定按 `page` 处理，可直接复用现有参数保存和存储过程取值链路。

#### 2.3 编辑回显规则

标准库编辑页面无需额外新增数据库标识字段，可直接通过 `gjj_ywbzksx.ywblbzdx` 是否为空判断当前记录类型：

- `ywblbzdx` 有值：按“对象属性”模式回显。
- `ywblbzdx` 为空：按“自定义属性”模式回显，并回填“属性名称”“属性编码”。

#### 2.4 业务规则页参数配置

业务规则页面中的参数配置区域继续根据 `gjj_ywbzksx` 动态生成录入控件，但需区分两类属性：

- 当 `ywblbzdx` 有值时，保持当前对象属性方式，继续渲染为下拉选择。
- 当 `ywblbzdx` 为空时，按自定义属性方式渲染为文本输入框，允许直接录入对应值。

参数保存时仍以 `ywblbzsx` 作为参数编码，以 `sxbm` 作为展示名称，不额外引入新的参数结构。

#### 2.5 存储过程兼容性

由于自定义属性统一保存为 `sxly=page`，现有存储过程和函数中基于 `page` 分支读取页面参数的逻辑可继续复用。

因此本次改造无需为“自定义属性”单独扩展新的存储过程分支，也无需引入额外数据库执行语义。

## 改造点 12：业务规则页面新增 AI 政策分析辅助清册勾选

### 1. 改造目标

在业务规则页面“清册选择”弹窗中新增“AI 政策分析”能力，支持业务人员输入政策文本后，系统结合当前关键数据算法、业务内容分类、候选业务办理标准及已选结果发起 AI 分析，并返回建议勾选的业务办理标准列表，辅助完成清册筛选。

本次改造目标是补齐“政策文本 -> AI 分析 -> 勾选结果同步 -> 用户提示”这一完整辅助链路，不替代人工最终确认，也不改变现有业务规则保存模型。

### 2. 逻辑改造

#### 2.1 分析入口与触发条件

- AI 政策分析入口放置在业务规则页面“清册选择”弹窗的查询区域。
- 仅当已选择关键数据算法，且最大可提取额场景已选择业务内容分类时，允许发起分析。
- 用户输入政策文本后，点击“AI 政策分析”按钮发起分析请求。

#### 2.2 AI 输入上下文

AI 分析时，需将以下上下文一并传递给后端，再由后端组装为工作流输入：

| 输入项 | 说明 |
| --- | --- |
| 政策文本 | 用户在弹窗中录入的原始政策内容 |
| 当前关键数据算法 | 对应 `ywsf/gjsjsf` |
| 当前业务内容分类 | 对应 `ywnrfl` |
| 清册筛选条件 | 当前输入的业务办理标准、业务办理标准描述关键字 |
| 候选标准列表 | 当前算法和业务内容分类下的可选业务办理标准 |
| 已选结果 | 当前机构下已同步到业务规则表的标准结果 |

说明：

- 候选标准列表用于帮助 AI 在限定范围内输出更准确的勾选结果。
- AI 输出结果原则上仅返回建议勾选的标准 ID 列表及简短说明。
- AI 不直接写库，仍由后端统一做结果校验和同步。

#### 2.3 Dify 工作流配置页面

AI 政策分析能力需接入现有 Dify 工作流配置页面进行维护，支持新增和修改配置。

配置要求建议如下：

| 配置项 | 说明 |
| --- | --- |
| page_key | 固定配置为业务规则页面对应标识，例如 `business_rule` |
| workflow_name | 工作流名称，例如“政策分析” |
| workflow_type | 需在配置页面中选择 `ai_analysis`，用于标识 AI 分析类型 |
| api_url | Dify 工作流调用地址 |
| api_key | Dify 工作流密钥 |
| enabled | 是否启用 |
| description | 备注说明，可填写“业务规则清册 AI 政策分析” |

配置页面交互要求：

- 在现有“AI 工作流配置”页面中，新增配置时支持选择工作流类型。
- 修改已有配置时，支持回显并修改 `workflow_type`。
- 当当前页面用途为业务规则清册 AI 分析时，`workflow_type` 需选择或默认带出 `ai_analysis`。
- 同一 `page_key` 下允许按不同 `workflow_type` 维护多条配置，便于后续扩展报告生成、总结归纳等其他 AI 能力。

#### 2.4 后端工作流调用

后端新增 AI 政策分析接口，建议继续使用页面级工作流配置方式：

- 根据页面标识 `page_key` 和工作流类型 `workflow_type` 查询启用中的工作流配置。
- 将政策文本和候选标准列表组装为工作流入参后调用 Dify 工作流。
- 工作流执行成功后，解析返回内容中的 `selectedIds` 和 `summary`。
- 若 AI 未返回可识别的标准 ID，则按失败处理并返回明确提示。

说明：

- Dify 配置相关接口可复用现有 `server/routes/http/dify-config.js`。
- 创建配置时 `workflow_type` 默认值可保持为 `ai_analysis`，但页面上仍建议显式可选、可回显、可修改。

#### 2.5 结果同步与勾选处理

- 后端拿到 `selectedIds` 后，需复用现有业务规则同步逻辑，将 AI 建议结果同步到 `gjj_ywbz`。
- 同步前继续执行互斥关系校验，防止 AI 返回互斥标准导致脏数据入库。
- 同步成功后，接口返回最新勾选 ID 列表及成功提示文案。
- 前端收到成功结果后，自动在清册弹窗中勾选当前页命中项，并保留后续人工调整能力。

#### 2.6 提示与交互说明

- AI 分析弹窗中增加说明提示，告知用户建议先将每页显示条数设置为最大后再执行分析，以便一次性查看更多命中结果。
- AI 成功后，页面需弹出成功提示，明确说明“已自动勾选当前页命中结果”，并提示可先调整每页显示条数后重新分析。
- AI 失败时，需直接展示失败原因，例如未配置工作流、未返回可匹配标准、存在互斥标准等。

#### 2.7 范围与边界

- 本次 AI 分析仅作用于业务规则页面“清册选择”弹窗，不扩展到标准库页面。
- 本次以“辅助勾选”为目标，不自动代替用户点击“保存”之外的其他确认动作。
- 本次不要求将 AI 返回的完整推理过程长期落库，仅保留必要的同步结果和提示信息。
